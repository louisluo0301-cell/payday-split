# PaydaySplit 后续优化方案：从收入分账到自动预算账户

更新日期：2026-11-18。定位：Reactive Omni / **Set It and Forget It**。

产品承诺：用户一次设定预算、授权边界和异常处理偏好，之后每笔可识别收入自动归集、分配、记录；只有需要补充资金、权限或风险决策时才打扰用户。自动化依赖来源链事件、Reactive 执行、目标链回调、授权及费用余额，不承诺无条件即时执行。

本文是后续建设方案。以下明确标为“规划”的能力尚未实现，不能用于宣传已支持跨链资金搬运、自动月度重置或真实投资收益。

## 1. 合约核心逻辑

### 1.1 瀑布＋比例双模式

规划 `AllocationMode { Waterfall, ProRata }`，模式是规则版本的一部分；切换需预演和用户确认，旧版本回调保持拒绝。复用同一预算、目标、权限和执行内核，避免两套风控产生差异。

- **Waterfall**：保留当前语义。桶的请求额为 `fixed + floor(grossIncome × bps / 10000)`，按顺序扣减；先固定账单再税务/储蓄由模板显式排序。每次支出受剩余收入、目标余额、资金预算约束。
- **ProRata**：仅使用比例，要求固定额为零；比例和不超过 10000。先确定可分配预算 `B = min(income, availableBalance, allowance, runLimit, dailyRemaining, protocolRemaining)`，再计算 `floor(B × bps / 10000)`。这里的百分比基数是 **B**；瀑布仍是毛收入，界面必须说明区别。
- 为避免顺序偏向，比例模式先计算完整金额向量再执行；目标封顶、失败或停用桶释放的金额默认保留，不自动放大其他桶比例。舍入尾差保留；指定尾差桶也要通过其目标和限额校验。
- 例：收入 1000，单次上限 600，权重 50%/30%/20%，比例模式支付 300/180/120、保留 400。瀑布同样的 50%/30%/20% 会按毛收入请求 500/300/200，受 600 预算截断为 500/100/0。

统一会计等式：`confirmedPaid + pendingReserved + retained = acceptedIncome`。现有非托管直付模式 `pendingReserved = 0`；所有路径必须满足总支出不超过收入与用户/协议限制。

### 1.2 动态资金桶

当前已可编辑整组桶；下一步新增 `addBucket / updateBucket / removeBucket / reorderBuckets`，底层仍最多 8 桶，批量操作一次递增版本并发事件。

采用稳定 `bucketId` 与独立 `priority`，不再把数组位置作为永久身份。删除使用停用标记并从活动序列移除；历史付款仍可按 ID 查询。金额、比例、收款方、用途、目标、策略适配器均为显式字段，标签存前端或内容哈希以控制 gas。

变更语义：只改标签不改变链上规则；改权重/顺序生成新版本；换收款方生成新桶 ID。周期进度若需要继承，必须以明确迁移操作保留相同所有者、资产和收款方，不能因为排序默默清零。v6 目前按规则版本隔离目标，任何真实桶变更都会开启全新目标命名空间，界面已提示。

### 1.3 原生 ETH 与 ERC20

统一内部资产标识 `AssetId(chainId, token)`，原生资产使用明确哨兵值，18 位精度；WETH 与 ETH 分开列示。禁止将执行费用余额当作用户收入或预算资金。

- **ERC20**：保留钱包 `approve + transferFrom` 路径；按资产配置，不接受无界任意代币。默认只支持标准 ERC20，转账税、重基准、恶意余额回报需专门适配。
- **ETH**：普通 EOA 没有 ERC20 授权机制，普通转账也没有可订阅的 ERC20 `Transfer` 日志。首选用户专属 `IncomeReceiver`，`depositNative(planId, receiptNonce)` 收款并发标准收入事件，Reactive 再触发受限分配；另可规划智能账户模块。用户需要把发薪地址改为该收款地址。
- 收款适配器属于有合约余额的新模块，须提供用户独立提现/退出、分账失败可领取余额和总负债账本；管理员不能救援用户本金。无标识 `receive()` 只记入可认领余额并提示，不能猜测收入所有者。强制转入 ETH 也不能产生虚假发薪事件。
- 原生转账使用有界 `call`；收款方拒收时保留可领取余额或记录失败，不阻塞其他桶。先更新状态，再外部调用，防重入。用户可选择 WETH 路径简化集成，但不能声称其等价于 EOA 原生收入自动扣款。

### 1.4 发薪周期额度重置

v6 仅支持用户显式“Start new cycle”，目标启用后的成功付款才计入进度，不补算启用前付款。自动重置在 M1 实现：

- 固定周期配置 `{anchorUtc, duration, carryPolicy}`，支持每周/每两周/30 天；30 天不能称为自然月。到期与单日限额都使用 UTC。
- 按收入源事件的区块时间确定 `cycleId = floor((incomeTimestamp-anchor)/duration)`。目标额度账本按 `(user, asset, bucketId, cycleId)` 隔离，重试使用原周期并保留原预留；防止月底失败、月初重试双拿额度。
- 目标链需要来自受认证 Reactive 消息的来源区块时间和稳定事件 ID；不接受外部用户随意提交时间。延迟窗口之外、已封账周期转入人工处理。单次/当前日风控在实际执行时再次检查，不能因收入归属旧周期绕过今天支出上限。
- 懒重置：下一笔收入访问新周期账本即可，无需每个用户每月单独跑定时交易。没有收入就无需为重置付 gas。
- 自然月需单独日历算法，明确定义 UTC 月末及 28/29/30/31 日；先独立测试，再加入模板。默认不滚存未完成目标，开启滚存必须有累计上限。

### 1.5 超额资金与溢出策略

新增 `OverflowPolicy { Retain, NextEligible, DesignatedBucket }`；默认 Retain，保持当前非托管体验。

瀑布中某桶目标已满时，未支出部分可继续流向后续合格桶。指定溢出桶必须在同一计划内、不能指向自身，并受目标和风控约束；一轮最多经过 8 桶，不允许递归溢出。比例模式默认不重分配目标/失败释放额，若用户选择 NextEligible，应采用明确的第二轮规则且仍有界执行，预演显示两轮金额。

溢出不能绕过暂停、每日额度、冷静期或跨链最小金额；无可用去向即保留或可领取。现有 v6 已具备瀑布继续后续桶、最终留在钱包的基础行为。

## 2. 适配 Reactive 的风控安全

### 2.1 回调认证与故障分类

继续使用 Omni 的 `onlySystem`、`SYSTEM = 0x8888…8888`、`requestCallbackV_1_0`，目标链同时校验 Callback Proxy 和被注入的 Reactive 合约地址。payload 首参数必须是 `address(0)` 占位。Reactive 的请求与目标链执行是两笔交易，不能在 `react()` 中用普通 `try/catch` 捕获未来目标链失败。[官方 Reactive 合约文档](https://dev.reactive.network/reactive-contracts)

接收方有 debt 时回调被阻止；失败尝试也会消耗目标链原生币，因此重试前必须检查费用与失败原因。不能把加次数当作可用性保障。[官方回调文档](https://dev.reactive.network/callback-contracts)

| 故障 | 自动处理 | 需要用户的情况 |
|---|---|---|
| RPC/中继暂时不可用、确认未终结 | 等待确认，延后检查 | 超过 SLA 或重组冲突 |
| Proxy 拒绝/回调 OOG、整笔回滚 | 经认证失败凭证或确认未执行后重新投递同一 eventId | 达到重试上限、需要提高 gas 超过用户预算 |
| 桶转账失败、交易整体成功 | 只重试已登记的失败桶和原预留金额 | 黑名单、授权不足、用户暂停 |
| 规则已更新、来源超期、权限不符 | 终止，不套用新规则自动重做 | 用户选择显式恢复或放弃 |
| 费用不足/debt | 暂停队列，提示补充费用 | 扣款/自动充值需事先授权限额 |

### 2.2 有界失败重试队列

下一代采用 `IncomeJob` 状态机：`Observed → Confirmed → Requested → Executing → Completed / Partial / Waiting / Cancelled / Expired`。用户看到“已请求”与“已完成”的区别。底层至少区分交易级失败和桶级失败。

1. 事件去重 ID：`keccak256(sourceChainId, emitter, user, asset, originTxHash, logIndex)`；桥消息、流式提取增加适配器类型和 nonce 域。v6 单部署去重键暂为 `(user, token, txHash, logIndex)`，多链前必须升级。
2. 首次执行固定 `ruleVersion`、金额向量、各桶成功位图和失败原因；逐桶重试只能支付未成功桶的未清余额。不能重跑整条固定账单，也不能从客户端任意更改 payee/amount。
3. v6 已经执行成功或逐桶跳过的来源事件会被标记 processed；`recoverSplit` 只适合未消费的来源键，**不能**宣称其已支持失败桶重试。新增队列需要新存储结构和合约版本。
4. 重试预留失败桶的周期目标及待支出额度，防止其他收入填满额度后再重试形成超额。取消/到期释放预留；实际支付再转入 paid。非托管 ERC20 的预留只限制预算，不锁住钱包资金，仍需重新读余额和授权。
5. 每次重试重新检查暂停、授权、保留余额、实际执行日及协议限额；若可用预算不足则等待，不静默改动已确认金额。用户主动修改目标导致冲突时取消待执行项并提示。
6. 默认最多 3 次尝试、建议退避 1/5/30 分钟、24 小时 TTL；这些是可配置产品默认值，不是网络保证。到点需要一个触发事件或执行服务，智能合约不会自行醒来；每轮批处理最多 8 项且不能扫描无界用户列表。
7. 首选订阅目标链结果日志和 Proxy 失败日志驱动状态；部署前核对实际 ABI。只有“没有看到成功”不足以证明失败，超时也不能直接发另一笔无去重的支付。
8. 开放执行者只可调用已经入队的任务，不能创建任意来源事件；自动化服务失效后用户仍可对同一任务手动执行。重试费用有每任务、每用户和协议总预算。

### 2.3 多层限额

保留当前 `reserve / maxPerRun / dailyLimit / minIncome / validUntil / paused`，新增每桶每周期额度和 `(chainId, asset)` 协议总日限额、全局暂停。用户与协议所有限额取最严格值，手动执行、重试、溢出、桥和生息入口共用会计内核。

跨资产不能直接相加原始单位：黑客松先按 token 限额；未来美元总限额依赖有时效检查的可信预言机、精度统一和价格偏离熔断。跨链“全局”限额不能靠多链各自一份计数保证，采用中心预算授权＋各链预分配配额，断网时不得增额，防止并发透支。

回调 gas、最大尝试次数和原生手续费另设上限，不能和用户本金预算混账。高费率或循环收入触发熔断；自己给自己、桶退款和 A→B→A 收入环继续过滤并配合冷却时间/来源白名单。

### 2.4 精细化权限

| 身份 | 权限 | 限制 |
|---|---|---|
| 用户/用户 Safe | 创建规则、选策略、授权、提款、暂停 | 仅操作自己的资产和计划 |
| Emergency Guardian | 立即暂停协议/有风险适配器 | 不改收款方、不提款、不解锁；恢复需管理员延迟确认 |
| Governance 多签＋Timelock | 注册适配器、调整协议上限、发布版本 | 延迟生效；旧版本用户可退出；不能代替用户选择风险策略 |
| Keeper/Retry executor | 投递已确认任务、推进状态 | 无任意转账权、不能重写金额或收款人 |
| Notifications/Indexer | 读取事件、发送用户已订阅通知 | 无签名/资金权限；最小化个人信息 |

现有 owner 为 Ownable2Step；不要为了展示分权把当前非代理合约随意改成可任意升级的 owner 后门。会话密钥只限任务方法、资产、金额、期限和链，禁止无界执行授权。紧急暂停立即生效，增额、改策略和升级延时生效。

### 2.5 全链路事件与账本

规划统一 `planId / eventId / jobId / bucketId / attempt / ruleVersion / sourceChainId / destChainId / cycleId` 关联字段。核心事件包括 `IncomeObserved, ExecutionRequested, BucketPaid, BucketFailed, RetryScheduled, JobCompleted, OverflowApplied, CycleOpened, StrategyDeposited, BridgeInitiated, BridgeFinalized, PolicyChanged`。较大元数据放内容哈希，避免昂贵重复日志。

索引器显示来源交易 → Reactive 请求 → 目标回调 → 逐桶结果；每个跨链段分别显示确认状态和手续费。成功指标必须以实际结果为准；恶意 token 发出的事件不能替代资产到账验证。重组回滚索引记录、重新核对终局，日志不可证明税务合法性。

## 3. 前端交互体验

### 3.1 可视化预算仪表盘

主视图分为收入、固定账单、税务、储蓄、消费五列，显示金额流向；比例模式使用堆叠条/环形图，两个模式共用桶卡片。每桶展示本周期目标、已付、待处理、剩余额度和预计达标；首页展示钱包可用余额、预算保留、可消费额和费用续航。

“可消费额”必须扣除用户选择的保留额/锁定额，待跨链/生息资产单独显示，不能把预估收益算成现金。拖动排序后立即预演差异；保存前汇总新增收款方、授权变化和生效周期。手机可用上下移动替代拖动；颜色不是唯一状态提示，金额有清晰币种/网络标签。

### 3.2 分配结果模拟预演

v6 已有 `previewExecution`，读取当前目标、政策、余额、授权、暂停与每日已花费；`previewWaterfall` 仍是忽略目标/限制的基础数学预览。下一步每桶输出 `requested / cappedByGoal / cappedByPolicy / payable / skippedReason` 并加执行前后对比。

模拟场景包含收入骤降/暴增、授权不足、周期切换、待重试占额、桥费/滑点、生息失败和停用桶。真实执行前再 `eth_call` 检查；展示区块号、时间和费用估计，提醒状态会变化。标准 token 的数学可精确复现，黑名单/代币税/跨链延迟无法保证，应明确显示假设。

### 3.3 异常通知

第一层站内状态，无需外部账号：待确认、部分成功、欠费、授权不足、规则过期、目标已达。第二层由用户主动订阅邮件/Web Push/Telegram；采用 outbox 队列、eventId 去重、签名 webhook、失败退避和退订，隐藏公开页面中的收入明细。

默认成功结果每日摘要，只有需要行动的异常即时通知；例如“税务桶因授权不足未支付 50 USDC，已暂停重试”，附链上证据与处理入口。通知服务不持有资金密钥，通知失败不改变分账结果。服务中断后补发摘要，不重复轰炸。

### 3.4 规则模板库

内置四个有版本的模板：自由职业者（固定房租＋税务＋储蓄）、DAO 工资（固定工资＋奖金）、学生预算（生活费上限＋储蓄目标）、紧急储备（优先填满目标后保留）。模板包含模式、周期、目标、默认上限和解释，但收款地址必须由用户填写。

税务比例只作为可编辑示例，不按地区宣称准确税率；模板不上线即启用生息/桥/锁定。预演通过后保存，一次签名只覆盖明确动作。JSON 备份校验版本、链、资产、精度和金额；恢复只载入草稿，不恢复权限或伪造已付进度，沿用 v6 边界。

## 4. 跨链与流式工资

### 4.1 多链收入源统一监听

先做“多链可见、各链本地分配”：`SourceRegistry` 白名单注册 `(sourceChainId, emitter, asset, user, adapterType)`，Reactive 按确切合约/用户 topic 订阅，避免全网 Transfer 监听。每源独立确认策略、最小收入和次数预算；跨链钱包归属通过用户签名绑定，不能仅假设相同地址由同一人控制。

以事件 ID 域隔离去重；币种按链和地址识别，不凭 USDC 名称合并。UI 可以合并展示资产估值，但资金仍各链独立。部署时核对 Reactive 实际支持网络、Proxy 地址与费用，网络地址不硬编码在模板里。

### 4.2 跨链资金分发

Reactive 是触发/编排层，不能凭一个回调把源链 ERC20 变成目标链资产。跨链规划单独的 `BridgeAdapter`，先选一种经过评估且支持目标资产/链的桥；不在核心合约内实现自己的桥。[Reactive 请求回调的范围](https://dev.reactive.network/reactive-contracts)

资金路径：来源收入确认 → 用户已授权的桥适配器锁定/销毁 → 桥消息确认及资产释放 → 目标 Receiver 验证可信桥、来源域、token、beneficiary、nonce → 发 `BridgedIncome` → Reactive 请求当地分账。只能以实际释放金额执行，不能在 bridge initiation 时乐观支付第二次。

消息和资产分别跟踪，状态包括 Initiated/Relaying/Received/Distributed/Refunded；过期不自动再次锁源资产，恢复沿同一 messageId。用户设桥费上限、minReceived、deadline、接收资产及失败退款地址，默认不跨链。小额收入在源链聚合到阈值再桥接，提现退出和聚合等待时间清晰显示。

桥故障或目标链暂停时隔离该桶，其他本地桶正常执行。不能承诺多链原子成功。首个演示限制为双链、单资产、单桥，保留无桥的主路径。

### 4.3 对接流式工资

候选采用 Sablier 的可提取工资适配器，或 Superfluid 的显式结算/快照适配器；第一期只完成一个。Sablier 类提款须核验协议部署、streamId 的接收人及第三方提款权限；不得让执行者替换收款人。[Sablier 官方 FAQ](https://docs.sablier.com/support/faq)

Superfluid 余额可随流协议动态变化，因此不能假设每秒都有一条 ERC20 Transfer 可供订阅。需要定期结算触发或适配器提款/包装，发出标准 `IncomeSettled` 事件后才进入现有分账内核；同时处理包装资产、可支配余额和流出负债。[Superfluid Super Tokens](https://docs.superfluid.org/docs/concepts/overview/super-tokens)

按最小金额或最长间隔聚合工资，避免每秒付一次回调费用。每个结算 nonce 仅消费一次；暂停/终止工资流不会清空已有凭证。流协议和提现适配器引入独立信任/权限边界，不把它们直接列入当前标准 ERC20 支持范围。

## 5. 增值金融模块

### 5.1 储蓄桶自动生息

先支持单一、白名单 ERC-4626 同资产策略，用户主动选择。分配到储蓄桶后，适配器原子拉取该次批准金额并 `deposit(assets, user)`，份额直接归用户；若采用用户专属 Vault，则需明确持有人和独立退出权。用户保持自己的提取权，管理员不能赎回用户份额。

所有适配器仅由可信分账器触发，拉款不能使用调用者随便填的 from；验证 `vault.asset()`、额度、暂停和输出份额。设 `minShares`、到期时间、单次/总敞口上限；allowance 用后清零，不给无限策略授权。`previewDeposit` 受链上状态影响，不能当稳健价格预言机，需额外滑点和异常份额价格防护。[ERC-4626 标准与安全考虑](https://eips.ethereum.org/EIPS/eip-4626)

失败时整个子调用回滚，回退为普通用户储蓄地址或保留，不能先扣款再留下不明归属余额。策略退出、提款暂停、损失和清算风险必须显示，不承诺本金或 APY；总资产＝可用现金＋按当前可赎回价值估计的份额，收益与本金分列。首期排除异步赎回、杠杆、自动换币和收益最高自动轮换。

### 5.2 税务归集与凭证

税务桶只完成资产预留，不自动向税务机关申报/缴税。增加年度/周期报告，记录收入来源、毛收入、实际税务预留、币种精度、来源和目的链交易、时区、规则版本、冲正及桥费。

导出 CSV/JSON 和可阅读 PDF，凭证包含 reportId、生成区块范围和数据哈希；法币估值若开启，要标记历史报价源、时间、币种、缺价状态。禁止用今天价格反填所有历史收入；不能把跨链桥两端、自己转账和策略赎回重复当新收入。类别/成本基础由用户或会计确认，报告属于记账辅助。

### 5.3 消费预算冷静期锁定

普通钱包里的 retained 无法靠 UI 强制锁定。规划独立、可选 `CooldownAccount`，用户选择把消费预算转入该合约，形成 `tranche(amount, unlockAt)`；到期领取由用户触发，或按事先授权的目标自动释放。先提供 24/72 小时等固定时长，不支持管理员改收款人。

已有 tranche 不得被管理员缩短或延长锁期，新配置仅影响新存入资金。紧急退出政策必须在存入前选定：严格锁定，或允许即时退出并明确该机制只是行为约束。两种不能混称不可绕过锁仓。紧急事件可暂停新存入，已到期用户提现尽量保持可用；状态和退出路径独立于 Reactive 费用是否充足。

## 6. 工程交付、升级与审计

### 6.1 测试矩阵

| 类型 | 必测边界及不变量 |
|---|---|
| 单元/边界 | 0/1/最大金额、0/8/9 桶、bps 总和、空/停用桶、整数尾差、目标恰满/不足/降低、同规则重复保存 |
| 周期/模式 | 锚点之前、边界前后 1 秒、月底/闰年、漏过多个周期、跨期延迟重试、切换模式和重排后的进度归属 |
| 代币/原生 | 6/18 位、无返回/false/revert、黑名单、恶意重入/虚假余额、ETH 拒收、强制 ETH、费用余额与本金隔离 |
| 状态 fuzz/invariant | 任意配置、收入、目标、暂停、重试顺序；总支出＋预留不超授权预算；成功桶永不重复；退出负债≤资金；用户/资产/链不串账 |
| Reactive/跨链 | 错 Proxy/Reactive/来源域、重复/乱序/重组、过期旧版本、OOG、欠费、队列饱和、桥两端重复确认、退款后延迟消息 |
| DeFi/流式 | vault 份额突变/暂停/限额、滑点、撤销授权、提现延迟、流停止/重启、负实时余额、适配器故障隔离 |
| 前端/运维 | 草稿不自动发送交易、网络切换/断开、备份篡改、模拟与链上差异、通知去重、手机/键盘操作、RPC 切换 |

当前基线 72＋13 是 v6 实测，不是上述全部规划测试已完成。新增模块进入主路径前，分别提供测试结果、可复现命令和故障演示；不能仅为追求覆盖率数字添加镜像实现测试。

### 6.2 合约升级方案

近期坚持不可变核心、版本化部署。v6 需要重新部署，不能直接升级旧地址。迁移顺序：暂停旧规则 → 处理/取消旧待执行任务 → 导出草稿 → 部署新核心/Reactive并绑定 → 用户检查并保存新规则/目标 → 撤销旧授权 → 仅给新地址有限授权 → 小额验收。旧规则/目标进度不得未经用户确认直接复制；旧新两套自动监听不得同时有效。

长期如确需代理，先独立设计 UUPS/Transparent 的存储布局、initializer、升级多签和 timelock；锁定实现合约、阻止重复初始化、检查升级授权与存储兼容。当前 callback proxy 和 Reactive 地址有 immutable/绑定语义，代理迁移需要重新论证，不能仅套模板部署。资金持有模块与自动化核心分离，用户始终有不依赖升级管理员的退出路径。

### 6.3 审计适配

提供架构/资产流/权限矩阵、状态机、外部依赖及固定版本、信任假设、所有入口的额度扣减路径、事件字典和已知风险。为 `transferBucket` 的外部 self-call、恶意 token、失败收费、周期预留、跨链消息认证和所有 rescue 方法提供专项说明。

静态分析使用 Slither 等工具分级复核，Foundry lint 告警逐条解释；“工具通过”不等于已审计。准备 invariant handler、差分预演模型、gas 上限回归和链上代码验证。审计发现按严重级修复并重新验证；新增桥/生息模块触发额外审查，不继承核心合约的结论。

### 6.4 一键部署与可复现交付

保留本地 `script/local-demo.ps1`，加多网络配置驱动入口 `deploy.ps1 -Environment testnet -Config ...`。配置含 chainId/RPC、Proxy/System、资产精度、来源白名单、费用预算和角色；预检链身份、地址代码、钱包余额和限额，禁止把示例地址当真实部署结果。

步骤：固定依赖并运行检查 → 生成部署计划 → 部署核心与适配器 → 绑定 Reactive 和回调 → 最小权限配置 → 注资执行费 → 保存一次规则事件建立订阅 → 小额完整流程 → 验证源码 → 输出 manifest、地址、哈希、ABI、版本及前端配置。记录每步便于断点恢复，已绑定实例不重复绑定；私钥不写入产物/日志。

CI 覆盖格式、测试、构建、运行时代码大小、依赖/密钥扫描；真实广播是显式部署操作。交付包保留 SHA256 清单、变更说明、历史素材标识及验收证据。`npm run local:goals` 复现三次完整本地回调，验证 350 目标下房租实付 **300 → 50 → 0**，预演与实际余额一致，重复投递不再付款。

## 7. 演示脚本与产品验收

黑客松主线只讲一件事：“不规律收入自动完成每期预算”。推荐 3–5 分钟：

1. 选自由职业模板，填收款地址、房租目标、税务/储蓄比例和支出上限，预演 1000 收入。
2. 一次保存后收两笔收入，展示固定账单只补足目标、其余继续分配；展示目标、已付和保留余额。
3. 模拟一个失败桶或授权不足，其他桶不受影响；状态明确，恢复不重复支付已成功桶。
4. 在 M1 实现后推进一个发薪周期，下一笔收入自动使用新周期额度；当前 v6 演示必须写“手动新周期”。
5. 导出凭证和方案备份，指出本地/测试网环境与尚未集成的金融模块。

优先衡量：完整流程成功率、重复支出次数（必须为 0）、异常可恢复率、用户每周期需要操作次数、每笔收入的总手续费。跨链延迟按每段测量并展示分位数；不能以本地 Mock 的耗时宣传真实网络性能。

长期以“默认自动、风险有界、失败可解释、用户能退出”为验收标准。生息、桥和锁定都是用户主动选择的模块，主收入分账无需依赖任何一个模块才能运作。

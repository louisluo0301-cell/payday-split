PaydaySplit turns an incoming stablecoin payment into an ordered waterfall — fixed bills, tax, savings, remainder retained — with one Reactive callback instead of a keeper.

“Which chain, which event, what trigger, what action — and why Reactive?”

02TRIGGER

When does it fire?

Only when all of these are true:

✓to is a subscribed user
✓token matches the rule
✓amount ≥ minPaycheck
✓rule active · version fresh
✓per-user + global budget
✓(txHash, logIndex) unseen

Self-transfers and refunds from your own payees are ignored. One paycheck consumes one callback.

Failure isolated. A bad payee only skips its bucket; the amount stays available for the next bucket and is never redirected to the keeper.
EXAMPLE1,000 dUSDC → rent 300 + tax 250 + savings 150 → 300 retained.

What would this take otherwise?

MANUALOpen the wallet, compute the split, send 3–8 transfers on every payday.
KEEPERA server, a private key, gas, monitoring, retries — and it can go down.
EXCHANGEOpaque auto-transfer, custodian risk, limited rules.
With Reactive: one subscription → one callback → no server, no private key, no polling loop.
But the cost is real: lREACT callback budget, Lasna liveness, one token per deployment, and a minimum paycheck.

WHY IT IS DIFFERENT

Not a notifier. It mirrors the rule and version, maintains the subscription, filters self/refund transfers, enforces per-user and global budgets, and authenticates the callback payload.
